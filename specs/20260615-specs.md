# PocketLM API — SDD Plan

**Date:** 2026-06-15  
**Version:** 20260615

## 1. Purpose
Build a small, clean, production-oriented API for a lite agent using **FastAPI**, **LangChain**, and **LangGraph**. The agent should handle simple tasks reliably, with an emphasis on maintainability, testability, and low operational overhead.

## 2. Product Goals
- Provide an HTTP API for simple agent tasks.
- Use LangChain/LangGraph to orchestrate tool use and task flow.
- Support optional short-term memory via in-process checkpointers.
- Include rate limiting / backpressure for slow upstream APIs.
- Follow clean code principles and keep the system easy to extend.
- Add tests early and keep architecture modular.

## 3. Scope
### In scope
- FastAPI application skeleton.
- Agent execution endpoint(s).
- LangGraph workflow for simple task handling.
- LangChain integration for prompts, tools, and model abstraction.
- Optional memory/checkpoint support.
- Rate limiting / request throttling for slow or expensive calls.
- Basic observability and error handling.
- Test suite and developer workflow.

### Out of scope (initially)
- Multi-user auth / permissions.
- Complex long-term memory or vector DB.
- Multi-agent coordination.
- UI/frontend.
- Heavy enterprise deployment concerns.

## 4. Assumptions
- Python 3.13+.
- Package management via `uv`.
- API-first design.
- The actual model/provider is model-agnostic via an abstraction layer.
- Simplicity is preferred over premature generalization.

## 5. Proposed Architecture
### Layers
1. **API layer**
   - FastAPI routers, request/response schemas, dependency injection.
2. **Application layer**
   - Use cases: run agent, validate input, manage rate limits, manage checkpoints.
3. **Agent layer**
   - LangGraph graph definition and execution.
   - LangChain prompt/tool/model composition.
4. **Infrastructure layer**
   - Model providers, storage/checkpoint adapters, rate limiting adapters.

### Key components
- `app/main.py` — FastAPI app entry.
- `app/api/` — routes and schemas.
- `app/agent/` — graph, prompts, tools.
- `app/memory/` — checkpoint/memory abstraction.
- `app/services/` — orchestration and business logic.
- `app/core/` — config, logging, common errors.
- `tests/` — unit and integration tests.

## 6. Functional Requirements
- Accept a task/request via HTTP.
- Execute a lightweight agent workflow.
- Return structured output.
- Optionally persist short-term conversation state.
- Enforce rate limits or concurrency limits for slow APIs.
- Provide consistent error responses.

## 7. Non-Functional Requirements
- Keep latency low.
- Keep codebase modular and readable.
- Avoid tight coupling to one model provider.
- Ensure tests can run deterministically.
- Keep dependencies minimal.

## 8. API Surface (draft)
- `GET /health` — health check.
- `POST /agent/run` — execute a single task (classification or summarization).
- `GET /version` — app/version info.

## 9. Memory / Checkpointer Plan
- Start with an abstraction, not a hard dependency.
- Support in-memory checkpointing for development.
- Allow pluggable persistence later (Redis, SQLite, Postgres, etc.).
- Make memory optional per request or per endpoint.

## 10. Rate Limiting / Slow API Strategy
- Add async request throttling at the app/service boundary.
- Add concurrency limits for expensive calls.
- Consider timeouts and retries with sane defaults.
- Make provider-specific limits configurable.

## 11. Testing Strategy
### Unit tests
- Request validation.
- Agent orchestration logic.
- Rate limit behavior.
- Checkpointer abstraction.
- Error mapping.

### Integration tests
- FastAPI endpoints.
- End-to-end agent execution with mocked dependencies.
- Memory enabled/disabled scenarios.

### Test principles
- Prefer deterministic mocks over live model calls.
- Test business logic separately from HTTP transport.

## 12. Code Quality Plan
- Follow clean code and separation of concerns.
- Keep functions small and explicit.
- Use typed interfaces and pydantic schemas where helpful.
- Introduce linting/formatting/tooling early if needed.

## 13. Milestones
### M0 — Project setup
- Create app package structure.
- Add FastAPI baseline and health endpoint.
- Define config and logging.

### M1 — Agent skeleton
- Build LangGraph flow for classification and summarization tasks.
- Add model-agnostic LangChain model interface.
- Return structured responses.

### M2 — Memory and limits
- Add optional in-process checkpointing.
- Add async rate limiting / concurrency control.
- Add timeout and retry policy.

### M3 — Tests and hardening
- Add unit/integration tests.
- Improve error handling and validation.
- Document run/test workflow.

### M4 — Extensibility
- Add tool interface.
- Add provider abstraction.
- Prepare for additional endpoints or workflows.

## 14. Open Questions
1. Which model provider should we target first?
2. Do we want memory persisted in-process only at first, or a real store?
3. Should the API be synchronous, asynchronous, or both?
4. Which agent task types are in scope for v1?
5. Do we want auth now or defer it?

## 16. Decisions Confirmed
- Model provider: **model-agnostic**.
- Memory: **in-process only**.
- API style: **async**.
- v1 task types: **classification** and **summarization**.
- Auth: **none**.
